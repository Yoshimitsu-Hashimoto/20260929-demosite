# AIと作るWordPressサイト — 構築からテスト・修正まで

静的なWebサイトを、仕様書をもとにAI（Claude Code）でWordPress化し、テスト、GitHub Issue、修正まで進めます。

## 全体の流れ

```
① リポジトリを用意する
      ↓
② Dockerでローカル環境を作る
      ↓
③ 静的サイトをWordPress化する
      ↓
④ テスト計画を作る
      ↓
⑤ Playwrightでテストする（＋コードの確認）
      ↓
⑥ GitHub Issueを立てて直す
```

| ステップ | やること | 目安 |
|---|---|---|
| ① | GitHubにリポジトリを作る | 5分 |
| ② | DockerでWordPressを起動し、初期設定する | 10分 |
| ③ | 静的サイトを仕様書どおりにWordPressテーマにする | 25分 |
| ④ | 仕様書からテスト計画を作る | 10分 |
| ⑤ | Playwrightでテストし、コードも確認する | 15分 |
| ⑥ | 見つかった問題をIssueにして直し、再テストする | 10分 |

どのステップも、AIに頼む → 人が結果を確かめる、の繰り返しです。

## 事前に準備してあるもの

### ファイル

| ファイル | 内容 |
|---|---|
| `docs/spec.md` | サイトの仕様書。何を満たせば合格かを、仕様ID（SPEC-01など）付きで書いている |
| `docs/test-data.md` | テストデータ。制作実績10件（うち下書き1件）、業種4つ（うち実績0件が1つ）など |
| `static-site/` | WordPress化する前の静的サイト（HTML・CSS・画像） |
| `compose.yaml` | Docker環境の定義（WordPress、データベース、Mailpit、WP-CLI） |
| `docker/mu-plugins/local-mail.php` | WordPressから送ったメールを、外部ではなくMailpitに届ける設定 |
| `theme/` | 空のフォルダ。ここにWordPressテーマを作る |

### ツール

| ツール | 使いみち |
|---|---|
| Docker Desktop | WordPressをローカルで動かす |
| Claude Code | 作業を頼むAI |
| GitHub CLI（`gh`） | リポジトリとIssueをAIから操作する |
| Node.js | Playwrightを動かす |

### 題材のサイト

架空の制作会社「株式会社ひなた」の実績紹介サイトです。

- 制作実績の一覧と詳細（業種で絞り込める）
- 実績ごとの情報：顧客名・制作年・担当範囲
- お問い合わせフォーム（送信するとメールが届く）

## ① リポジトリを用意する

**ねらい**：作業の記録を残し、あとでIssueを使えるようにする。

> 講座のあとに自分で試す場合は、GitHubのテンプレートリポジトリ（[Yoshimitsu-Hashimoto/2026-09-29-ai-wordpress-course](https://github.com/Yoshimitsu-Hashimoto/2026-09-29-ai-wordpress-course)）の「Use this template」で自分のリポジトリを作り、cloneすれば①は完了です。②から進めてください。

AIへの依頼：

```text
このフォルダをgitリポジトリにして、GitHubに公開リポジトリ hinata-wp-demo を作って push してください（gh を使う）。
```

**確かめること**：GitHubにリポジトリができ、ファイルが入っている。

---

## ② Dockerでローカル環境を作る

**ねらい**：誰のPCでも同じWordPressが動く環境を用意する。

`compose.yaml` で起動するもの：

| サービス | 役割 | URL |
|---|---|---|
| wordpress | WordPress本体 | http://localhost:8090/ |
| db | データベース（MariaDB） | ― |
| mailpit | 確認用メールボックス | http://localhost:8091/ |
| wpcli | WordPressをコマンドで操作する | ― |

AIへの依頼：

```text
compose.yaml を使ってDockerでWordPressを起動し、WP-CLI（docker compose run --rm wpcli wp ...）で初期設定してください。
- サイトURL http://localhost:8090 、サイト名「株式会社ひなた」、管理者メールアドレス admin@example.test、日本語、タイムゾーン東京、パーマリンクは /%postname%/
- 管理者のユーザー名とパスワードはテスト用の値にして README に書く
```

**確かめること**：サイト・管理画面・Mailpitが開ける。

---

## ③ 静的サイトをWordPress化する

**ねらい**：仕様書を渡して、AIに「何を満たせばよいか」を伝えたうえで作ってもらう。

AIへの依頼：

```text
static-site/ の静的サイトを、docs/spec.md の仕様どおりにWordPressテーマ化してください。テーマは theme/ に作る（WordPressでは hinata というテーマ名になる）。
- 制作実績はカスタム投稿タイプ、業種はカスタムタクソノミー、顧客名・制作年・担当範囲はカスタムフィールド（プラグインは使わない）
- 実績一覧は業種で絞り込めるようにする（/works/?industry=<スラッグ>）
- お問い合わせフォームはテーマ内で処理し、wp_mail で管理者に送る
- docs/test-data.md のテストデータをWP-CLIで投入する
- できたらブラウザで各ページを確認し、コミットして push する
```

**確かめること**
- 実績一覧で業種を選ぶと絞り込まれる
- 実績の詳細に、顧客名・制作年・担当範囲が出る
- お問い合わせを送ると、Mailpitにメールが届く

---

## ④ テスト計画を作る

**ねらい**：「動いたように見える」ではなく、仕様書どおりかを確かめる準備をする。

AIへの依頼：

```text
docs/spec.md と docs/test-data.md をもとに、テスト計画を docs/test-plan.md に作ってください。
テストID・仕様ID・手順・期待結果を書き、正常系・異常系・境界条件（0件、未入力、未公開の実績など）を含める。
```

**確かめること**（AIの計画に入っているか）
- 絞り込みの結果が0件になる場合
- 下書きの実績が表示されないこと
- 制作年が未入力の実績の表示
- 必須項目が未入力、同意にチェックがない場合に送信できないこと
- 送信完了の表示だけでなく、メールが届くこと

---

## ⑤ Playwrightでテストする

**Playwrightとは**：ブラウザを自動で操作して、画面の表示や動きを確かめるテストツール。テストをコードとして残すので、修正したあとも同じ条件で何度でも確かめられる。

AIへの依頼（テスト）：

```text
docs/test-plan.md のテストを Playwright でテストコードにして実行してください。
- Playwright の準備（npm install など）もしてよい
- メールの到着は Mailpit の API（http://localhost:8091/api/v1/messages）で確かめる
- 不合格があっても、期待結果やコードは変えずに結果を報告する
```

AIへの依頼（コードの確認）：

```text
テーマのコードを、仕様書と照らしてレビューしてください。仕様とずれている所や、バグになりそうな所があれば挙げてください（まだ修正はしない）。
```

**確かめること**：テストの合格・不合格の数、不合格の内容、レビューで挙がった点。

---

## ⑥ GitHub Issueを立てて直す

**ねらい**：見つかった問題を、あとから誰が見ても分かる形で記録し、それをもとに直す。

AIへの依頼（バグが見つかった場合）：

```text
見つかったバグのうち <どれか1つ> を GitHub Issue にしてください（gh issue create、ラベル bug）。
仕様ID、再現手順、期待結果、実際の結果、修正後に確認するテストを本文に書く。
```

AIへの依頼（バグが見つからなかった場合は、機能追加のIssueにする）：

```text
実績一覧に「制作年で並べ替え」を追加する GitHub Issue を作ってください（gh issue create）。
やること、仕様への追記案、確認するテストを本文に書く。
```

AIへの依頼（修正）：

```text
Issue #<番号> を gh issue view で読み、ブランチを作って対応してください。
テストを追加・実行して全部通ることを確かめ、コミットして push し、Issue に結果をコメントしてください。
```

**確かめること**：Issueの内容、修正の差分、テストが全部通ったこと、Issueへのコメント。

---

## まとめ

**仕様書 → 構築 → テスト計画 → テスト → Issue → 修正 → 再テスト** が、仕様IDでつながりました。

人がやること：
- 仕様書を書く（AIが合否を判断できるように、具体的に）
- AIが作った計画や結果を確かめる（抜けている観点を指摘する）
- 修正で、テストの期待結果を都合よく変えていないかを見る
